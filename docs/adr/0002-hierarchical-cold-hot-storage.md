# ADR 0002: 分级冷热存储架构设计

- **状态**: Accepted
- **决策日期**: 2026-09-16
- **参与者**: 藏书阁核心架构组

## 背景与问题

长篇网络小说动辄数百甚至上千万字。如果将长篇小说正文、章节目录及高频变动的阅读进度、书架排序全部存储在单个 SQLite 关系数据库或 SharedPreferences 中：
1. **数据库体积膨胀**：几本百万字小说就能让 SQLite 文件膨胀到数百兆，导致每次打开数据库或查询书架元数据极度缓慢；
2. **读写并发锁死**：后台离线全本下载大量章节写入 DB 时，前台用户翻页读写容易发生锁死或 I/O 阻塞；
3. **数据丢失风险**：清理缓存时极易误删关键的用户进度。

## 决策

我们决定采取分级冷热存储分离架构（`HierarchicalStorage`）：

1. **热数据层 (Hot Data)**：
   - **载体**：轻量关系数据库 (SQLite) 与 SharedPreferences / KV 存储；
   - **职责**：仅保存书籍元数据（标题、作者、封面、来源 URL）、书架顺序、当前阅读章节与 `charOffset` 字符级锚点、书签批注标记。
2. **冷数据层 (Cold Data)**：
   - **载体**：应用独立沙盒文件系统中的纯文本文件（`chapters/{bookId}/{chapterIndex}.txt`）；
   - **职责**：存储已下载或嗅探解析后的章节纯文本内容。
3. **清理与运维准则**：
   - 个人中心与系统存储清理只允许清理冷数据目录（`chapters/`），用户触发清理时数据库中的书籍与进度毫发无损。

## 后果与影响

- **正面收益**：核心数据库体积始终保持极小（数兆以内），查询书架秒开；后台多线程并发下载直接向沙盒写独立文件，零 DB 锁竞争；离线缓存易于统计与原子清空。
- **负面成本**：需要通过服务层对章节文件的存在性与合法性进行抽象管理（缺失时触发即时网络嗅探或备用源补全）。
